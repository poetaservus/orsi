# Personal Vault phase 2: engine and persistence contract

9 October 2026. Implements roadmap sections 2.1, 2.2 and 2.3. Entry point:
`app.vault.engine.Vault`. This engine is intentionally not connected to startup,
conversation/image consumers, credential providers or UI. Those are later phases.
See [verification](vault-phase2-verification.md) for measured checks and deferred
qualification. The [phase 1 storage map](vault-phase1-storage-map.md) still defines
the intended scope of personal data.

## Format v1

The first durable engine format is `orsi-personal-vault`, version `1`. The frozen
phase 1 experiment retains its distinct `orsi-vault-prototype` identifier and is
rejected by this engine. No personal-data migration or implicit format upgrade is
implemented. This document finalizes the phase 1 candidate's wrapper/catalog
encoding before any application consumers are connected.

```text
<vault>/header.json
<vault>/state.bin
<vault>/.lease
<vault>/objects/<random-id>.bin
<vault>/objects/<random-id>.pending
<vault>/.pending-<random-id>           # encrypted catalog/header staging
<vault>/backups/<random-id>/          # verified managed ciphertext snapshot
<vault>/backups/.pending-<random-id>/  # uncommitted ciphertext snapshot
```

Profile IDs are random canonical UUIDs and survive relocation/restore. Location,
drive letter and Windows identity are never key inputs. Local and portable modes
call the same engine with an explicitly supplied root. Default location/discovery
and public profile-locator UI remain later work. Creation requires a new root and
preserves existing directories. Unlock validates the limited header before
creating a lease, then re-reads it under the lease before authentication.

Header fields are exactly `format`, `version`, `profile_id`, `cipher`, `password`,
`recovery`, `auth`. The optional recovery slot's presence is now explicitly public
security metadata. No private name, quota, preference, project path or credential
value is added to the public header. Header bound is 16 KiB.

Generate a random 64-byte master bundle containing independent 32-byte personal
and credential keys. The password slot contains `kdf` and `wrapped_keys`; the KDF
has `name`, `operations`, `memory_bytes`, `salt`. Argon2id13 uses a random 16-byte
salt. The initial candidate remains two operations/64 MiB; accepted costs are
bounded at 2–6 operations and 64–256 MiB before derivation. The minimum-host cost
decision is deferred at the user's instruction.

XChaCha20-Poly1305 AEAD wraps the bundle. The password wrapper authenticates the
format/version/profile, its role and KDF metadata. An optional recovery wrapper
uses an independently random 32-byte recovery key and authenticates its separate
role. Both wrappers contain the library-generated nonce. `auth` is AEAD of empty
plaintext under the personal key, authenticating the canonical full header except
`auth` itself. This binds all security fields/slots while permitting password
rewrapping without possessing the separate recovery key. Unknown versions,
duplicate/extra fields, invalid sizes/costs and failed authentication are rejected.

`change_password` rewraps the bundle and replaces only the header. The object
bytes are unchanged. `generate_recovery_key` is an explicit call returning its
32 secret bytes once; the plaintext recovery key is never retained in a file,
environment or bootstrap record. Rotation replaces the active recovery wrapper;
`disable_recovery` removes it. There is no password reset backdoor. After recovery
unlock, explicitly set a new password. Future UI must explain keeping a recovery
copy separately from the vault disk and must not display/export it automatically.

## Catalog and objects

`state.bin` is an authenticated encrypted catalog, bounded to 16 MiB plaintext.
It contains schema version, revision, quota, personal records, separately encrypted
credential catalog, managed-backup IDs/times and backup policy. Credential names,
relationships and values are not exposed by decrypting only the personal catalog
envelope. All nonces are generated by the library; no persistent nonce counter is
invented. Catalog contexts authenticate format, version, profile ID and role.

The catalog maps encrypted logical paths to opaque object IDs, authenticated
plaintext sizes, reference lists, retained-root flags and expiration times.
Relative names are never passed to host filesystem operations. Reject absolute,
traversal, drive, backslash and invalid Unicode paths. Each domain is limited to
10,000 records; each record has at most 1,024 same-domain references.

Object encoding uses a 24-byte libsodium secretstream header followed by frames
with four-byte big-endian ciphertext lengths. Data frames hold at most 1 MiB and
use MESSAGE tags. An empty FINAL frame must terminate the stream, with no trailer.
Associated data binds format/version/profile, object role, ID and key domain.
The catalog carries names/metadata, so durable objects do not need the prototype's
metadata-first frame. Per-object plaintext limit is 512 MiB. Every frame is
authenticated and size-bounded; truncation, absent FINAL, altered/order-dependent
frames, extra bytes, object substitution and wrong-domain access fail validation.

Source writes stream bounded byte chunks. Ordinary reads authenticate the entire
object into RAM before returning any bytes. Unlock and backup verification use
discarding verification streams rather than accumulating full images in memory.
No decrypted temporary file is created. A later bounded media-stream adapter can
be designed without changing this consumer safety boundary.

## Atomicity and failure recovery

`write_batch` builds and validates the complete target reference graph, stages
encrypted blobs, flushes/fsyncs each blob, publishes them, then atomically replaces
one encrypted catalog. The catalog replacement is the visibility/ownership commit
point. A record, source, preview, extraction and derived index can commit together.
The previous catalog/objects stay intact until replacement succeeds.

If a process dies before commit, reopening uses the old catalog and reclaims
unreferenced encrypted staging/final objects. If it dies after commit, reopening
uses the new catalog and its already-published objects. An error after catalog
replacement has an uncertain caller-visible outcome: final blobs are preserved
until reopening authenticates the actual committed catalog. They are never
blindly deleted in exception cleanup. No host tool is retried or replayed here.

On unlock, verify header, catalogs and every live object before orphan cleanup.
Authenticated corruption enters recovery-required and preserves originals.
Missing/read-only/I/O-failed storage enters unavailable, drops key/catalog
references and releases the process lease. The API never creates replacement
storage for a disappeared root or falls back to plaintext. Quota rejection leaves
the current session/committed records usable; abandoned encrypted files remain
accounted for until cleanup/reopen. Unknown storage entries are preserved and
reported rather than swept as if they were owned staging.

Windows uses existing non-following snapshot handles and ancestor directory pins;
the OS lease locks one byte of a dedicated regular file. Reject reparse/symlink
chains and hardlinked lease files. Other instances cannot obtain the same lease;
OS process death releases it. Stale lease files do not imply an active owner.
Lock closes all owned handles, permitting explicit relocation. The non-Windows
flock implementation aids testing but does not qualify another OS for v1.

File fsync, atomic replacement and POSIX directory barriers are implemented.
Windows physical power-loss/media durability still depends on the filesystem,
device and hardware qualification. Passing process-termination tests is not a
claim that arbitrary failed disks/controllers preserve data. Corrupt/incomplete
committed data fails closed for explicit recovery/restore.

## Quota, physical space and backups

The default quota is 1 GiB and does not preallocate storage. Count actual file
lengths for headers, catalog, objects, previews/index records, encrypted staging,
orphans and retained managed backups. The root lease byte is disposable overhead
excluded from encrypted usage. Actual free disk space is checked separately with
a 1 MiB safe-write reserve. Runtime/model/app files remain outside this accounting.

Streaming admission reserves ciphertext growth and a conservative catalog staging
allowance. Catalog/header replacement requires room for both old and staged new
metadata. Consequently a quota must cover transient encrypted staging, not merely
the final visible payload. `set_quota` rejects limits below current usage or below
the safe atomic update's required space. Raising the quota changes the encrypted
catalog, without recreating objects. With insufficient space, retry after managing
backups/orphans, enlarging the limit or freeing the containing disk; no implicit
outside export occurs.

`backup()` creates a managed snapshot under `backups/`. `backup(destination)` makes
an explicitly requested independent ciphertext copy at a new separate location.
Only header, a fresh encrypted catalog and referenced blobs are copied; backups
are not recursively copied. All copied records/assets are verified before a
managed snapshot is published and before any prior managed copy is retired.
Failed snapshots leave only encrypted orphans for safe cleanup. Existing explicit
destinations are preserved, never replaced or merged.

Managed defaults: at most three copies and 30 days. `BackupPolicy` supports count
and age changes; age zero disables age-based expiry, count zero disables/removes
managed copies. Explicit policy changes and `prune_backups` commit the retained
set before physical cleanup. Creation order resolves equal-second timestamps so
the newest verified copy survives. Independent backups are never discovered,
rewritten or deleted by managed retention and do not consume the source vault's
quota. Their containing disk is checked when creating them.

`Vault.restore` authenticates/verifies the source, creates a new destination,
reopens/verifies it and returns an unlocked engine. Password or recovery-key
unlock is supported. Source and existing destinations remain intact; there is no
automatic synchronization. Source needs an engine lease, so a busy or unwritable
source is reported safely. A same-disk backup helps corruption recovery; a separate
device/copy is needed for loss recovery. Actual SSD/second-host exercises remain
deferred, as requested.

## Retention, access and key lifetime

`RecordWrite` declares a retained root or an unretained dependent asset, its
references and optional expiration. Reachability from retained roots preserves
shared assets. Deleting/expiring a root removes its unshared source/preview/text/
index chain while preserving dependencies owned elsewhere. Explicit deletion of
a named dependent also removes its references. Catalog commit removes normal
read/list visibility before physical cleanup, so an interrupted sweep cannot
resurrect a deleted record or stale index. Unreachable cycles are not retained.

`put_temporary` defaults to 24 hours, adjustable from one second through 30 days.
Expired records are hidden by read/list immediately, even before `expire` commits
cleanup. Retained unknown tool outcomes must not use automatic temporary expiry;
their owning consumer must retain them until acknowledged. Profile/application
adapters in phase 3 will apply the storage-map category defaults.

Independent and managed encrypted backups can retain deleted data, prior
credentials and old password/recovery wrappers. Deletion/rotation does not revoke
already copied keys or erase previous backups. Catalog revisions do not provide
hardware-backed rollback prevention. Application deletion is not guaranteed
physical erasure on an SSD.

The engine emits no logs or diagnostic payloads, and errors contain fixed messages
without content/secret/path values. Internal catalog/key references are dropped on
lock/error, and owned bytearray keys are best-effort overwritten. Python, native
libraries and the OS may retain other copies, paging or crash dumps. Always call
`lock` or use the unlocked engine as a context manager. Application job admission,
provider-session release, profile switching, path/tool exclusions and media cache
clearing remain phase 3 integration work; the engine alone does not sandbox host
code or protect an unlocked/compromised machine.

Cryptographic primitives remain PyNaCl 1.6.2/libsodium high-level AEAD/secretstream.
See the primary [PyNaCl AEAD documentation](https://pynacl.readthedocs.io/en/latest/secret/)
and [Windows file-sharing contract](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew).
Independent format/key/recovery/path review remains deferred by the user and is
required before describing the complete product as security-qualified.
